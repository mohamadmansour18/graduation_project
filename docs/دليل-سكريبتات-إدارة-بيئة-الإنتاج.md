## نظرة عامة سريعة

| السكربت | متى يُستخدم؟ | ما الذي يقوم به؟ |
|---|---|---|
| `common.sh` | لاستخدامه كمكتبة مشتركة من باقي السكربتات | يحدد مسارات الإنتاج، يغلّف Docker Compose، يوفّر التحقق، الأقفال، التسجيل، وفحص الخدمات |
| `artisan.sh` | لتنفيذ أي أمر Artisan داخل حاوية التطبيق | يتحقق من البيئة ومن تشغيل خدمة `app` ثم ينفذ `php artisan` داخلها |
| `deploy.sh` | بعد سحب تعديلات جديدة على الكود | يبني صورة التطبيق، يفعّل وضع الصيانة، يعيد نشر الخدمات، ينفذ migrations وLaravel optimize، ثم يعيد Nginx |
| `reset-database.sh` | عند الحاجة لمسح قاعدة بيانات الإنتاج وإعادة تهيئتها بالكامل | ينفذ `migrate:fresh --seed` ثم يزامن Meilisearch ويرسل Scout imports عبر Queue |
| `health.sh` | بعد النشر أو عند تشخيص مشكلة | يفحص Docker وLaravel وقاعدة البيانات وRedis وMeilisearch وHorizon وHTTPS والـ failed jobs |
| `logs.sh` | لمراقبة السجلات أو تحليل الأخطاء | يعرض Logs لخدمة واحدة أو عدة خدمات أو كامل المشروع مع خيارات التتبع والزمن |
| `restart-services.sh` | بعد تعديل `.env.production` أو عند تعليق خدمة | يعيد إنشاء خدمات محددة دون Build، أو يعيد تشغيل الحاويات الحالية فقط |
| `up.sh` | لتشغيل البيئة بعد `down` أو بعد توقفها | يستخدم `docker compose up -d` افتراضيًا أو `start` للحاويات الموجودة |
| `down.sh` | لإيقاف البيئة مؤقتًا أو إزالة الحاويات والشبكة | يدعم `stop` أو `down` مع الحفاظ المقصود على الـ volumes |
| `renew-ssl.sh` | لتجديد شهادة Let's Encrypt | يشغّل Certbot renewal ثم يعيد تحميل Nginx عند نجاح التجديد |

<div class="warning">
لا تستخدم <code>reset-database.sh</code> على الإنتاج إلا عندما تكون متأكدًا تمامًا من أنك تريد حذف جميع بيانات قاعدة البيانات الحالية. هذه العملية غير قابلة للتراجع من دون نسخة احتياطية صالحة.
</div>

## قواعد الاستخدام العامة

### مكان التشغيل

نفّذ السكربتات من جذر المشروع:

```bash
cd ~/projects/graduation_project
```

ثم:

```bash
./scripts/production/<script-name>.sh
```

### ملفا الإنتاج المعتمدان

تعتمد السكربتات على:

```text
.env.production
docker-compose.production.yml
```

### جعل السكربتات قابلة للتنفيذ

```bash
chmod +x scripts/production/*.sh
```

### فحص الصياغة قبل الرفع

```bash
find scripts/production \
  -maxdepth 1 \
  -type f \
  -name '*.sh' \
  -print0 |
while IFS= read -r -d '' script; do
    echo "Checking: ${script}"
    bash -n "${script}" || exit 1
done
```

### فحص المسافات والأخطاء النصية

```bash
git diff --check
```

## `common.sh`

### المسؤولية

مكتبة مشتركة تستوردها جميع سكربتات الإنتاج بدل تكرار منطق Docker Compose والتحقق والتسجيل في كل ملف.

### متى نستخدمه؟

لا يُستخدم عادةً لتنفيذ عملية إدارية مباشرة. يتم استدعاؤه داخل السكربتات الأخرى عبر:

```bash
source "${SCRIPT_DIR}/common.sh"
```

يمكن تشغيله مباشرة فقط للتحقق من أن بيئة السكربتات الأساسية صحيحة.

### الصيغة

```bash
./scripts/production/common.sh
```

### ما الذي ينفذه؟

1. يفعّل الوضع الصارم في Bash:
   - `set -Eeuo pipefail`
2. يحدد جذر المشروع تلقائيًا.
3. يحدد:
   - `.env.production`
   - `docker-compose.production.yml`
4. يوفر دوال الرسائل:
   - `log_info`
   - `log_success`
   - `log_warning`
   - `log_error`
   - `die`
5. يتحقق من:
   - وجود Docker.
   - إمكانية الوصول إلى Docker daemon.
   - وجود ملفات الإنتاج.
   - صحة Docker Compose configuration.
6. يوفر الغلاف الموحد:
   - `production_compose`
7. يوفر أدوات فحص الخدمات:
   - `service_exists`
   - `require_service`
   - `service_is_running`
   - `require_running_service`
8. يوفر تأكيدًا نصيًا دقيقًا للعمليات الخطرة.
9. يوفر قفلًا باستخدام `flock` لمنع تشغيل نسختين متعارضتين من السكربت.

### الخيارات

لا توجد خيارات سطر أوامر عامة لهذا الملف.

## `artisan.sh`

### المسؤولية

تنفيذ أوامر Laravel Artisan داخل حاوية `app` باستخدام إعدادات Docker Compose الخاصة بالإنتاج.

### متى نستخدمه؟

عندما تريد تنفيذ أمر Artisan يدويًا على الإنتاج دون كتابة أمر Docker Compose الطويل.

### الصيغة العامة

```bash
./scripts/production/artisan.sh <artisan-command> [arguments] [options]
```

### أمثلة

```bash
./scripts/production/artisan.sh about
```

```bash
./scripts/production/artisan.sh migrate:status
```

```bash
./scripts/production/artisan.sh queue:failed
```

```bash
./scripts/production/artisan.sh scout:sync-index-settings
```

```bash
./scripts/production/artisan.sh scout:import "App\Models\Test"
```

### ما الذي ينفذه؟

1. يستورد `common.sh`.
2. يتحقق من وجود معامل واحد على الأقل.
3. يتحقق من صحة بيئة الإنتاج.
4. يتحقق من وجود خدمة `app`.
5. يتحقق من أن حاوية `app` تعمل.
6. ينفذ داخل الحاوية:

```bash
php artisan "$@"
```

7. يعيد نفس Exit Code الخاص بأمر Artisan.

### الخيارات

جميع الخيارات بعد اسم السكربت يتم تمريرها مباشرة إلى Artisan.

```bash
./scripts/production/artisan.sh --help
```

لعرض مساعدة السكربت، أو:

```bash
./scripts/production/artisan.sh help <command>
```

لعرض مساعدة أمر Artisan محدد.

## `deploy.sh`

### المسؤولية

تنفيذ دورة نشر تطبيق الإنتاج كاملة بعد وصول كود جديد إلى السيرفر.

### متى نستخدمه؟

بعد تنفيذ:

```bash
git pull origin master
```

واحتواء التعديلات على أي مما يلي:

- كود Laravel.
- ملفات Composer.
- Dockerfile.
- ملفات التطبيق التي تُنسخ داخل الصورة.
- migrations جديدة.
- إعدادات Laravel تحتاج إعادة Cache.
- تعديلات على خدمات التطبيق طويلة العمر.

### الصيغة

```bash
./scripts/production/deploy.sh
```

### ما الذي ينفذه؟

1. يتحقق من ملفات وأدوات الإنتاج.
2. يحصل على قفل نشر لمنع عمليتي Deploy متزامنتين.
3. يبني صورة خدمة `app`.
4. إذا كانت `app` تعمل:
   - يفعّل Laravel maintenance mode.
5. يعيد إنشاء خدمة `app` باستخدام الصورة الجديدة.
6. ينتظر حتى تصبح `app` في حالة تشغيل.
7. ينفذ:

```bash
php artisan migrate --force
```

8. ينفذ:

```bash
php artisan optimize:clear
php artisan optimize
```

9. يعيد إنشاء الخدمات طويلة العمر:
   - `reverb`
   - `horizon`
   - `scheduler`
10. يعيد إنشاء `nginx` لتجنب احتفاظه بعنوان IP قديم لحاوية التطبيق.
11. يتحقق من تشغيل الخدمات المطلوبة.
12. يعطّل وضع الصيانة.
13. عند حدوث خطأ بعد تفعيل الصيانة، يحاول تنفيذ:

```bash
php artisan up
```

حتى لا يبقى التطبيق عالقًا في وضع الصيانة.

### الخيارات

النسخة الحالية لا تحتاج خيارات؛ هدفها تقديم مسار نشر ثابت ومتوقع.

### لا تستخدمه عندما

- تريد فقط تشغيل حاويات متوقفة: استخدم `up.sh`.
- تريد فقط تطبيق تعديل على `.env.production`: استخدم `restart-services.sh`.
- تريد فقط إعادة تشغيل Horizon: استخدم `restart-services.sh --restart-only horizon`.

## `reset-database.sh`

### المسؤولية

حذف قاعدة بيانات الإنتاج بالكامل، إعادة تشغيل migrations والـ seeders، ثم إعادة بناء بيانات البحث.

### متى نستخدمه؟

- في مرحلة الإطلاق التجريبي قبل وجود بيانات حقيقية.
- عندما تريد إعادة تهيئة بيئة إنتاج تجريبية بالكامل.
- عند اتخاذ قرار واعٍ بمسح جميع البيانات.
- ليس كجزء من النشر الاعتيادي.

### الصيغة

```bash
./scripts/production/reset-database.sh
```

### التأكيد المطلوب

يطلب كتابة العبارة التالية حرفيًا:

```text
RESET-PRODUCTION-DATABASE
```

### ما الذي ينفذه؟

1. يتحقق من بيئة الإنتاج.
2. يتحقق من تشغيل:
   - `app`
   - `horizon`
3. يحصل على قفل خاص بعملية Reset.
4. يعرض تحذيرًا واضحًا ويطلب تأكيدًا نصيًا.
5. يفعّل وضع الصيانة:

```bash
php artisan down --retry=60 --refresh=15
```

6. يحذف الجداول ويعيد إنشاءها ويشغل Seeders:

```bash
php artisan migrate:fresh --seed --force --no-interaction
```

7. يزامن إعدادات Meilisearch:

```bash
php artisan scout:sync-index-settings --no-interaction
```

8. يمسح بيانات الفهرس القديمة ويرسل Import جديدًا لـ:

```bash
php artisan scout:import "App\Models\LibraryMaterial" --fresh --no-interaction
```

9. يكرر العملية لـ:

```bash
php artisan scout:import "App\Models\Test" --fresh --no-interaction
```

10. يتحقق أن Horizon ما زال يعمل لمعالجة Jobs.
11. يعطّل وضع الصيانة.
12. يوضح أن انتهاء السكربت يعني إرسال Jobs إلى Queue، وليس بالضرورة انتهاء فهرستها كلها.

### الخيارات

لا توجد خيارات في النسخة الحالية بسبب خطورة العملية ورغبتنا في إبقاء مسارها ثابتًا.

### ملاحظة عن Queue

عمليات `scout:import` عندك تستخدم Queue. لذلك قد يعود الموقع للعمل بينما لا تزال بعض وثائق Meilisearch تُفهرس في الخلفية.

راقب Horizon باستخدام:

```bash
./scripts/production/logs.sh horizon --follow --tail 200
```

## `health.sh`

### المسؤولية

إجراء فحوص قراءة فقط للتأكد من أن مكونات بيئة الإنتاج تعمل فعليًا، وليس فقط أن الحاويات في حالة `running`.

### متى نستخدمه؟

- بعد كل Deploy.
- بعد تشغيل البيئة.
- بعد تعديل `.env.production`.
- بعد Reset لقاعدة البيانات.
- عند ظهور `500` أو `502` أو `503`.
- قبل بدء تحليل مشكلة معقدة.

### الصيغة

```bash
./scripts/production/health.sh
```

### Exit Codes

| القيمة | المعنى |
|---:|---|
| `0` | جميع الفحوص الأساسية نجحت |
| `1` | يوجد فشل أساسي واحد أو أكثر |

التحذيرات وحدها لا تجعل Exit Code فاشلًا.

### ما الذي ينفذه؟

1. يتحقق من Docker وملفات Compose.
2. يفحص الخدمات المطلوبة:
   - `app`
   - `nginx`
   - `mysql`
   - `redis`
   - `meilisearch`
   - `reverb`
   - `horizon`
   - `scheduler`
3. يفحص الخدمة الاختيارية:
   - `ollama`
4. يقرأ حالة Docker Healthcheck إن كانت معرفة.
5. يتحقق من إقلاع Laravel عبر:

```bash
php artisan about --no-interaction --no-ansi
```

6. يختبر اتصال Laravel الحقيقي بقاعدة البيانات.
7. يرسل `PING` إلى Redis عبر إعدادات Laravel.
8. يصل إلى Meilisearch `/health`.
9. يتحقق من:

```bash
php artisan horizon:status
```

10. يحسب سجلات جدول `failed_jobs`.
11. يقرأ `APP_URL` ويرسل طلب HTTPS حقيقيًا.
12. يطبع ملخصًا:
   - `HEALTHY`
   - `HEALTHY WITH WARNINGS`
   - `UNHEALTHY`

### الخيارات

لا توجد خيارات في النسخة الحالية.

## `logs.sh`

### المسؤولية

عرض سجلات Docker Compose لخدمة واحدة أو عدة خدمات أو جميع الخدمات.

### متى نستخدمه؟

- عند تحليل أخطاء Laravel أو Octane.
- عند مراقبة Jobs في Horizon.
- عند تحليل مشاكل Reverb.
- عند ظهور خطأ Nginx مثل `502 Bad Gateway`.
- عند مطابقة خطأ مع وقت طلب أو Webhook أو عملية دفع.

### الصيغة العامة

```bash
./scripts/production/logs.sh [options] [service...]
```

### الخيارات

| الخيار | الوظيفة |
|---|---|
| `-f`, `--follow` | متابعة السجلات الجديدة مباشرة |
| `-t`, `--timestamps` | إظهار وقت كل سطر |
| `--tail <number\|all>` | تحديد عدد الأسطر الأخيرة |
| `--since <value>` | عرض السجلات منذ وقت أو مدة |
| `--until <value>` | عرض السجلات حتى وقت معين |
| `--no-color` | تعطيل ألوان Docker Logs |
| `-h`, `--help` | عرض المساعدة |

### أمثلة

جميع الخدمات:

```bash
./scripts/production/logs.sh
```

Laravel وOctane:

```bash
./scripts/production/logs.sh app --follow --tail 100
```

Horizon:

```bash
./scripts/production/logs.sh horizon --follow --tail 200
```

Nginx منذ آخر 30 دقيقة:

```bash
./scripts/production/logs.sh nginx --since 30m
```

عدة خدمات مع الوقت:

```bash
./scripts/production/logs.sh app nginx horizon \
  --follow \
  --tail 100 \
  --timestamps
```

فترة زمنية محددة:

```bash
./scripts/production/logs.sh app \
  --since "2026-07-24T20:00:00" \
  --until "2026-07-24T21:00:00"
```

### ما الذي ينفذه؟

1. يتحقق من بيئة الإنتاج.
2. يتحقق من صحة أسماء الخدمات المحددة.
3. يبني خيارات `docker compose logs`.
4. يعرض Logs.
5. في وضع `--follow` يبقى مفتوحًا حتى تضغط `Ctrl+C`.

## `restart-services.sh`

### المسؤولية

إعادة إنشاء أو إعادة تشغيل خدمات إنتاج محددة من دون Build ومن دون migrations.

### متى نستخدمه؟

#### الوضع الافتراضي: Recreate

استخدمه بعد:

- تعديل `.env.production`.
- تعديل إعدادات Compose التي تؤثر على خدمة.
- تغيير متغيرات Reverb أو Queue أو Mail.
- الرغبة في إنشاء حاوية جديدة من الصورة الحالية.

#### وضع Restart Only

استخدمه عندما:

- خدمة علقت.
- لم يتغير الكود.
- لم تتغير environment variables.
- لا تحتاج حاوية جديدة.

### الصيغة العامة

```bash
./scripts/production/restart-services.sh [options] [service...]
```

### الخدمات الافتراضية

عند عدم تحديد خدمات:

```text
app reverb horizon scheduler nginx
```

### الخيارات

| الخيار | الوظيفة |
|---|---|
| `--restart-only` | يعيد تشغيل الحاويات الحالية دون إعادة إنشائها |
| `--recreate` | يعيد إنشاء الحاويات دون Build، وهو الافتراضي |
| `--all` | ينفذ العملية على جميع خدمات Compose |
| `--wait-timeout N` | أقصى مدة لانتظار تشغيل كل خدمة، الافتراضي 60 ثانية |
| `--stop-timeout N` | مهلة إيقاف الحاوية في وضع restart-only، الافتراضي 30 ثانية |
| `-h`, `--help` | عرض المساعدة |

### أمثلة

إعادة إنشاء خدمات التطبيق الافتراضية:

```bash
./scripts/production/restart-services.sh
```

إعادة إنشاء Horizon وReverb:

```bash
./scripts/production/restart-services.sh horizon reverb
```

إعادة تشغيل Horizon فقط:

```bash
./scripts/production/restart-services.sh \
  --restart-only \
  horizon
```

إعادة إنشاء جميع الخدمات:

```bash
./scripts/production/restart-services.sh --all
```

### ما الذي ينفذه في الوضع الافتراضي؟

1. يتحقق من بيئة الإنتاج.
2. يحصل على قفل للعملية.
3. يحدد الخدمات المطلوبة.
4. يتحقق من وجودها في Compose.
5. ينفذ:

```bash
docker compose up -d --force-recreate --no-deps <services>
```

6. ينتظر وصول كل خدمة إلى حالة التشغيل.

### ما الذي ينفذه في `--restart-only`؟

1. يتحقق أن جميع الحاويات المحددة تعمل حاليًا.
2. ينفذ:

```bash
docker compose restart --timeout <seconds> <services>
```

3. ينتظر عودتها إلى حالة التشغيل.

<div class="warning">
وضع <code>--restart-only</code> لا يقرأ تعديلات جديدة في <code>.env.production</code> ولا يطبق تغييرات Compose. لتطبيقها استخدم الوضع الافتراضي الذي يعيد إنشاء الحاويات.
</div>

## `up.sh`

### المسؤولية

تشغيل بيئة الإنتاج كاملة أو تشغيل مجموعة خدمات.

### متى نستخدمه؟

- بعد تنفيذ `down.sh`.
- بعد توقف البيئة بالكامل.
- بعد إعادة تشغيل السيرفر إذا لم تبدأ الخدمات تلقائيًا.
- عند تشغيل خدمة محددة متوقفة.
- عندما تحتاج إنشاء حاويات أو شبكة مفقودة.

### الصيغة العامة

```bash
./scripts/production/up.sh [options] [service...]
```

### الخيارات

| الخيار | الوظيفة |
|---|---|
| `--start-only` | يشغّل حاويات موجودة ومتوقفة فقط |
| `--up` | يستخدم Compose Up، وهو الافتراضي |
| `--build` | يبني الصور قبل التشغيل |
| `--pull <always\|missing\|never>` | سياسة سحب الصور، الافتراضي `missing` |
| `--remove-orphans` | يحذف حاويات الخدمات القديمة غير الموجودة في Compose الحالي |
| `--wait-timeout N` | أقصى مدة لانتظار الخدمات، الافتراضي 120 ثانية |
| `-h`, `--help` | عرض المساعدة |

### أمثلة

تشغيل كامل البيئة:

```bash
./scripts/production/up.sh
```

تشغيل خدمات محددة:

```bash
./scripts/production/up.sh app nginx horizon
```

تشغيل الحاويات الموجودة فقط:

```bash
./scripts/production/up.sh --start-only
```

البناء ثم التشغيل:

```bash
./scripts/production/up.sh --build
```

سحب أحدث الصور الخارجية دائمًا:

```bash
./scripts/production/up.sh --pull always
```

### ما الذي ينفذه افتراضيًا؟

1. يتحقق من البيئة.
2. يحصل على قفل lifecycle.
3. يتحقق من أسماء الخدمات المحددة.
4. ينفذ:

```bash
docker compose up -d --pull missing
```

5. ينتظر وصول الخدمات إلى حالة التشغيل.

### الفرق بين `up` و`start`

| الأمر | ينشئ الحاويات المفقودة؟ | ينشئ الشبكات؟ | يطبق Compose الحالي؟ |
|---|---:|---:|---:|
| `up` | نعم | نعم | نعم |
| `start` | لا | لا | لا |

إذا سبق أن استخدمت `down.sh`، فلن يعمل `--start-only` لأن الحاويات حُذفت. استخدم `up.sh` العادي.

## `down.sh`

### المسؤولية

إيقاف بيئة الإنتاج مؤقتًا أو إزالة حاويات المشروع وشبكته مع الحفاظ على البيانات الدائمة.

### متى نستخدمه؟

#### `--stop-only`

- لصيانة قصيرة.
- لإيقاف خدمات مؤقتًا.
- عندما تريد تشغيلها لاحقًا بسرعة عبر `up.sh --start-only`.

#### الوضع الافتراضي `down`

- قبل صيانة طويلة.
- قبل تغيير جذري في Docker.
- عندما تريد إزالة الحاويات والشبكة وإعادة إنشائها نظيفًا.

### الصيغة العامة

```bash
./scripts/production/down.sh [options] [service...]
```

### الخيارات

| الخيار | الوظيفة |
|---|---|
| `--stop-only` | يوقف الحاويات دون حذفها |
| `--down` | يحذف الحاويات والشبكة، وهو الافتراضي |
| `--remove-orphans` | يحذف حاويات الخدمات القديمة |
| `--timeout N` | مهلة الإيقاف، الافتراضي 30 ثانية |
| `--yes` | يتجاوز تأكيد عملية down |
| `-h`, `--help` | عرض المساعدة |

### أمثلة

إيقاف مؤقت لجميع الخدمات:

```bash
./scripts/production/down.sh --stop-only
```

إيقاف Horizon وReverb فقط:

```bash
./scripts/production/down.sh \
  --stop-only \
  horizon reverb
```

إزالة حاويات وشبكة المشروع:

```bash
./scripts/production/down.sh
```

تجاوز التأكيد:

```bash
./scripts/production/down.sh --yes
```

### التأكيد في وضع Down

يطلب كتابة:

```text
DOWN-PRODUCTION
```

### ما الذي ينفذه في `--stop-only`؟

```bash
docker compose stop --timeout <seconds> [services]
```

الحاويات تبقى موجودة ويمكن تشغيلها بـ:

```bash
./scripts/production/up.sh --start-only
```

### ما الذي ينفذه في الوضع الافتراضي؟

```bash
docker compose down --timeout <seconds>
```

ويقوم بـ:

1. إيقاف جميع حاويات المشروع.
2. حذف الحاويات.
3. حذف شبكة Compose.
4. الحفاظ على Named Volumes.

<div class="danger">
السكريبت لا يدعم خيار <code>--volumes</code> عمدًا. لا تستخدم أوامر يدوية تحذف volumes الإنتاجية إلا ضمن خطة نسخ احتياطي واستعادة واضحة، لأن هذه الـ volumes قد تحتوي قاعدة بيانات MySQL وفهارس Meilisearch ونماذج Ollama.
</div>

## `renew-ssl.sh`

### المسؤولية

تجديد شهادات Let's Encrypt بطريقة آمنة ثم تطبيق الشهادة الجديدة على Nginx.

### متى نستخدمه؟

غالبًا لا تحتاج تشغيله يدويًا لأن `systemd timer` يشغله تلقائيًا. استخدمه يدويًا عند:

- اختبار عملية التجديد.
- تعديل إعدادات Certbot.
- التأكد من أن Nginx يستطيع تحميل الشهادة.
- معالجة مشكلة في التجديد التلقائي.

### الصيغة

```bash
./scripts/production/renew-ssl.sh
```

### ما الذي ينفذه؟

1. ينتقل إلى جذر المشروع.
2. يتحقق من ملفات Compose وبيئة الإنتاج.
3. يشغّل Certbot renewal باستخدام Webroot ومجلدات الشهادة المركبة.
4. إذا تم تجديد الشهادة:
   - يتحقق من صحة إعدادات Nginx.
   - يعيد تحميل Nginx أو يعيد إنشاء خدمته حسب تطبيق السكربت.
5. يسجل نتيجة العملية.
6. يعيد Exit Code مناسبًا ليتمكن systemd من تسجيل النجاح أو الفشل.

### التشغيل التلقائي

تدار العملية عبر:

```text
docker/production/systemd/graduation-ssl-renew.service
docker/production/systemd/graduation-ssl-renew.timer
```

### أوامر systemd المفيدة

عرض حالة المؤقت:

```bash
sudo systemctl status graduation-ssl-renew.timer
```

عرض موعد التشغيل القادم:

```bash
sudo systemctl list-timers graduation-ssl-renew.timer
```

تشغيل الخدمة يدويًا:

```bash
sudo systemctl start graduation-ssl-renew.service
```

عرض السجلات:

```bash
sudo journalctl \
  -u graduation-ssl-renew.service \
  --since "1 day ago"
```

## قائمة تحقق سريعة

- [ ] التعديلات مرفوعة إلى Git.
